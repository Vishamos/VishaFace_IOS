## 3. 얼굴 추적

| # | 내용 | 구분 | 근거 |
|---|---|---|---|
| 3.1 | ARKit 얼굴 추적(AR Foundation `ARFaceManager`, 전면 카메라). | 확정 | 준비 문서 §1 |
| 3.2 | **ARKit 얼굴 추적은 RGB 전면 카메라로 쓰고, TrueDepth(적외선 깊이 카메라)만 쓰지 않는다**(SE2에 없음, 깊이 값 없음. A12 이상이면 RGB만으로 ARKit 얼굴 추적 지원). 블렌드셰이프·시선은 같은 API로 나오지만 정확도가 낮을 수 있다(어두운 조명, 볼 부풀림·혀 같은 미세 표정). 방송 조명에서의 품질은 A2에서 확인한다. 노션의 "TrueDepth로 깊이값 이용" 문구는 노션 갱신 때 고친다. | 확정 | 사용자 결정 2026-11-22 (기기 사양) |
| 3.3 | 보낼 데이터: **블렌드셰이프 52개 + 머리 회전(쿼터니언)·위치**. 머리 자세는 `ARFace` Transform을 카메라 기준으로 바꿔 보낸다(VishasBody의 얼굴 회전 인식이 부정확해서 이 앱이 맡음). 시선은 블렌드셰이프 `eyeLook*` 8개로 보내고 눈 Transform은 보내지 않는다. 캐릭터 모델은 아직 없고 이 구성에 맞춰 만든다(눈을 본으로 움직이려면 받는 쪽에서 `eyeLook*` 값을 회전으로 바꾼다). | 확정 | 사용자 결정 2026-11-21, 22, 23 |
| 3.3b | 블렌드셰이프 좌우와 머리 자세는 **ARKit 값 그대로(거울 기준)** 보낸다. 앱에서 좌우를 뒤집지 않으며, 본인 기준으로 쓸지는 받는 쪽이 정한다. 측정값과 변환 방법은 프로토콜 §4a·§5a. 정면은 단위 회전. 위치 x 부호와 z가 거리(m)인지는 A2에서 확인 | 확정 (위치는 확인 필요) | 실기기 2026-11-23·24, GitHub issue #1, 사용자 결정 2026-11-24 |
| 3.3a | 표정은 정점 좌표가 아니라 **ARKit 블렌드셰이프(0∼1)**로 보낸다. 혀는 `tongueOut` 1개(내민 정도만), 시선은 `eyeLook{Up,Down,In,Out}` 좌우 8개(눈 Transform `ARFace.leftEye`·`rightEye`·`fixationPoint`는 보내지 않음, 3.3). | 확정 | 2026-11-18 논의, 사용자 결정 2026-11-22 |
| 3.4 | 프레임레이트 목표 **60 FPS** (`Application.targetFrameRate = 60`, Unity iOS 기본 30). 장시간 유지되는지 A3에서 실측하고, 발열로 안 되면 30으로 낮춘다. | 확정(목표) / 확인 필요(유지) | 사용자 결정 2026-11-22 |
| 3.5 | 블렌드셰이프 순서는 ARKit 이름 → 인덱스 고정 표로 정한다. | 확정 | 준비 문서 §3 |
| 3.6 | 얼굴 일부가 가려지거나 옆으로 돌아도 ARKit은 52개 값을 **모두** 준다(안 보이는 쪽은 추정 값, 항목별 신뢰도 없음). 추적이 끊기면 flags로 알리고 마지막 값을 보낸다(프로토콜 §5). 끊기는 각도는 A2에서 확인. | AI 제안 | ARKit 동작, 2026-11-21 논의 |

## 5. 통신

**헤더·등록 규격은 VishaSynapse가 기준**이고, 이 앱은 그 안의 데이터 부분만 정한다. 데이터 부분은 이 저장소의 **`docs/protocol/README.md`**(얼굴 데이터 프로토콜)에 두고, Vishamos는 그 문서를 보고 수신부를 만든다.

| # | 내용 | 구분 | 근거 |
|---|---|---|---|
| 5.1 | 전송: WebSocket(`ws://<서버 LAN IP>:<포트>`, 기본 4000) 하나로 등록·데이터. 인증 없음. | 확정 | Synapse 프로토콜 §1 |
| 5.2 | 명령(등록 등)은 JSON, 실시간 데이터는 바이너리 | 확정 | Synapse 프로토콜 §4 |
| 5.3 | 바이너리 헤더는 `[to, from]` 각 1바이트. **`from`은 앱이 22를 넣는다**(서버는 바꾸지 않음). 등록과 다르면 서버가 에러 없이 끊는다(1008 `from_mismatch`). | 확정 | Synapse 프로토콜 §4.2 |
| 5.4 | 데이터 부분 배치·종류 번호(`0x16`)·블렌드셰이프 순서는 얼굴 데이터 프로토콜(`docs/protocol/README.md`)이 기준이다. float32 그대로 보내고 1바이트 압축은 하지 않는다(60Hz × 250바이트 ≈ 15KB/s로 충분히 작음). | 확정 | 사용자 결정 2026-11-22 (전송 기준은 이 저장소에서 정함) |
| 5.5 | 숫자는 float32, 리틀 엔디언 | 확정 | Synapse 프로토콜 §4.2 |
| 5.6 | 목적지: **11**(Vishamos. 방송용·테스트용 모두 11). | 확정 | Synapse 프로토콜 §2 |
| 5.7 | 등록: 접속 직후 앱이 먼저 JSON `{"to":0,"from":22,"type":"client.register","data":""}`를 보낸다. **30초 안에** 안 보내면 끊긴다(1008). 응답 `client.registered`를 받은 뒤부터 바이너리를 보낸다. JSON 키는 소문자. | 확정 | Synapse 프로토콜 §3, §4.1 |
| 5.7a | 연결 유지: 서버가 30초마다 ping, 약 3분간 pong이 없으면 끊는다. `ClientWebSocket`은 **`ReceiveAsync` 대기 중일 때만** pong을 자동으로 보내므로 수신 루프를 항상 돌린다. | 확정(규격) / AI 제안(구현) | Synapse 프로토콜 §7 |
| 5.7b | 서버 에러는 JSON `type: "error"`, `data: {code, message}`. 바이너리 문제에는 에러가 오지 않는다. 앱은 에러 코드만 표시한다. | 확정 | Synapse 프로토콜 §5, §6 |
| 5.8 | 메시지 크기·빈도: 250바이트 고정 × 최대 60회/초. 서버 한도 64KB, Vishamos 수신 버퍼 1KB 이하. Synapse 프로토콜 §8 용량 표의 Face iOS 줄을 이 값으로 맞춘다(그쪽 저장소). | 확정 | Synapse 프로토콜 §4, §8 |
| 5.8a | 송신 구현: .NET 내장 `ClientWebSocket`을 쓴다(추가 라이브러리 없음). Android `SocketClient.cs`는 재사용하지 않고 다시 짠다 — 송신을 겹쳐 호출(60Hz에서 예외), `Aborted` 시 재접속 안 함, 매 송신 로그, IP 하드코딩, 추적·송신 혼재. 송신은 최신값 한 칸 + 단일 송신 루프로 한다. iOS 추가: **로컬 네트워크 권한**(거부하면 모든 접속 실패, `NSLocalNetworkUsageDescription`을 빌드 후처리로 `Info.plist`에 넣음), 앱 복귀 시 재접속. `ws://`는 ATS 대상이 아니다. | AI 제안 | `VishaFace/Assets/Scripts/SocketClient.cs` 검토 2026-11-21 |
